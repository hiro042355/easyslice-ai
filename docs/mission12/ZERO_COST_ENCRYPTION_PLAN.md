# Zero-cost custody strategy
Accepted source unchanged: AES-256-GCM token encryption, independent random32-byte DEK/message, authenticated envelope with wrapped DEK, numeric approved key version and AAD UID/app/environment/openID/generation/scopes/expiry/version, fail-closed startup/decryption, no plaintext persistence/browser/logs. Disconnect clears protected material under ownership checks. HMAC never encryption.

| Candidate | Qualification | Decision |
|---|---|---|
| Existing suitable managed provider | Only observed asia1 staging key MAC/HMAC; other locations/resources and remaining free operation allowances UNKNOWN | Reuse only if compatible permissions/zero incremental charge independently proved; no new usage now |
| GCP/AWS managed free claims | Billing/created key/version cost and restricted allowances; no evidence sufficient for zero-charge envelope service | New paid usage excluded; billing/payment requires owner approval, not activated |
| Secure application KEK | Could retain envelope design without per-call KMS bill, but KEK exportable into process and admin boundary weaker; secure provisioning/versioning/backup/revocation needed | Conditional design, not implemented/ready; no real deployment key generated |
| OpenBao self-hosted Transit | [Official engine](https://openbao.org/docs/secrets/transit/) supports AES256GCM, key versions/ACLs; [seal](https://openbao.org/docs/concepts/seal/) requires protected root/unseal recovery, restart unseals | Software may avoid license/service fee on existing host, but compute/storage/network/ops not free automatically; no instance installed/initialized |
| Local synthetic wrapping | Existing accepted test provider; ephemeral test-only material | Local tests only, never real secret-management evidence |

Current ManagedTokenVault/validateManagedKeyConfiguration are Google-specific: resource name regex + GOOGLE_SYMMETRIC_ENCRYPTION metadata + KMS_ENVELOPE audit semantics. Do not spoof these strings to insert software KEK/OpenBao, weaken HMAC/metadata checks or relabel LOCAL_TEST as deployment custody. SQL envelope v2 holds wrapped DEK and keyId, but application provider namespace/metadata/binding/rotation/AAD compatibility requires a separately reviewed narrow release. No live provider-neutral secret adapter is justified before owner selects a provider. Existing seam and diagnostics remain; new readiness gate explicitly blocks SOFTWARE_PROPOSAL/SYNTHETIC/HMAC.

Future application-envelope design: owner-approved high-entropy nonproduction KEK provisioned outside Git/CLI output/plaintext files; encrypted project-scoped host secret binding, process-only access, separately protected recovery copy. Immutable namespaced version; fresh per-message DEK/nonces and same AAD; authenticated wrapping protects DEK and AAD. Root KEK not derived from client secret/user password, not stored beside ciphertext or in same accessible DB, not printed in request/audit logs. Runtime may decrypt but cannot administer binding/key versions; separate operator rotation. Recover existing ciphertext with retained old versions; revoke/reencrypt/retire only after explicit recovery/retention approval. Host admins/compromised runtime can read exportable KEK; disclose this tradeoff, do not call it nonexportable managed KMS.

OpenBao would need dedicated nonprod auth/ACL/TLS/audit/storage and independent seal recovery, not dev-server/root token/static unseal shares beside data. No paid cloud auto-unseal. Secure operational availability and actual zero-charge hosting UNKNOWN. No real keys, no key material committed, no retention finalized. If required security boundary cannot be met free, report blocked rather than reduce custody.
