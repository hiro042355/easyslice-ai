## 1. Owner Identity Model Investigation

### 1.1 Where `owner_uid` is Generated and Injected
In NexCut AI, `owner_uid` is **never generated arbitrarily by the client or by background tasks**. It originates authoritatively from the authenticated session at the Next.js API route layer:
- **Authentication Route Guard (`lib/server/productionIdentity/routeGuard.ts:9-19`, `lib/server/productionIdentity/routeGuardCore.ts:30-49`):**
  Every API route verifying identity calls `requireAuthenticatedRequest(request)`. The route guard validates the session cookie (`__Host-nexcut_session`) or Authorization Bearer header using Firebase Admin Auth (`verifier.verifySessionCookie` or `verifier.verifyIdToken`).
- **Identity Projection (`lib/server/productionIdentity/firebaseIdentityAdapter.ts:63-74`):**
  `projectVerifiedIdentity` takes the decoded Firebase token and projects:
  ```typescript
  userId: decoded.uid as UserId
  ```
- **Asset Import API Entrypoint (`app/api/v1/assets/import/route.ts:15-21`):**
  ```typescript
  const authentication = await requireAuthenticatedRequest(request);
  if (!authentication.ok) return authentication.response;
  ...
  const result = await withProductionMediaRuntime(({ pool, bucket }) =>
    executeAssetImport({
      ownerUid: authentication.context.identity.userId,
      idempotencyKey: parsed.idempotencyKey,
      source: parsed.source,
      pool,
      bucket,
      signal: request.signal
    })
  );
  ```
  `ownerUid` is passed directly from `authentication.context.identity.userId`.
- **Adversarial Input Sanitization:**
  In `tests/urlAcquisition/productionAssetImportCommand.test.ts:19`, an adversary attempting to pass `{ ownerUid: "attacker" }` in the JSON request body is strictly rejected or ignored because the request boundary schema (`lib/server/assetImport/requestBoundary.ts`) extracts only `sourceUrl` and `idempotencyKey`, deriving `ownerUid` strictly from server authentication context.

### 1.2 Identity Equality: `owner_uid` vs Firebase UID
- `owner_uid` in the application and database is **100% identical** to the verified Firebase UID (`decoded.uid`).
- Throughout `workflow.jobs`, `workflow.media`, `workflow.exports`, and `workflow.asset_import_requests`, `owner_uid` represents the authenticated user's unique identity.

### 1.3 Database Verification and Constraints on `owner_uid`
When `owner_uid` is inserted into PostgreSQL:
- **Database Schema Constraints (`db/workflow/migrations/V000008__add_asset_import_idempotency.sql:1-33`):**
  - Type: `text NOT NULL`
  - CHECK Constraint: `CONSTRAINT ck_asset_import_owner CHECK (length(owner_uid) > 0)`
  - Primary Key: `PRIMARY KEY (owner_uid, idempotency_key)`
  - Foreign Key: `CONSTRAINT fk_asset_import_job_owner FOREIGN KEY (job_id, owner_uid) REFERENCES workflow.jobs(id, owner_uid) ON DELETE RESTRICT`
  - Note: In `V000008`, `job_id` is nullable. When `state = 'acquiring'`, `job_id` is `NULL`, so the foreign key to `workflow.jobs` is not evaluated during `claim`. However, if the row transitions to `succeeded`, `job_id` must reference an existing `workflow.jobs(id, owner_uid)` row!

### 1.4 Compatibility of `staging_test_tiktok_<RUN_ID>` with Existing Owner Identity Model
- **Evaluation:** Using `staging_test_tiktok_<RUN_ID>` satisfies `length(owner_uid) > 0` and is valid under PostgreSQL `V000008` schema constraints for rows in state `'acquiring'`, `'failed_retryable'`, or `'failed_final'` where `job_id IS NULL`.
- **Incompatibility with Full Lifecycle (`succeeded` state):**
  If a test row transitions to `state = 'succeeded'`, `job_id` is populated, requiring a parent row in `workflow.jobs` with the matching `(id, owner_uid)`. Unless a synthetic job is inserted into `workflow.jobs` with `owner_uid = 'staging_test_tiktok_<RUN_ID>'`, a foreign key violation (`23503`) occurs.
- **Security Boundary Violation:**
  `staging_test_tiktok_<RUN_ID>` is NOT an authenticated Firebase UID. It cannot call `POST /api/v1/assets/import` over HTTP because Firebase Auth cannot authenticate this synthetic UID without mock/emulator bypass. Therefore, this pattern only works for direct SQL test harnesses, NOT end-to-end API testing.

### 1.5 Risk of Synthetic UID Pollution in User Workflows
- **Accidental Collision:** Firebase UIDs generated by Google Identity Platform are 28–36 base64/alphanumeric characters (e.g., `qW8eR9...`). A synthetic string prefixed with `staging_test_tiktok_` will never be generated by Firebase Auth.
- **Cross-Tenant Access Risk:** In `lib/server/durableMediaOwnership/repository.ts` and `lib/server/assetImport/idempotencyRepository.ts`, all queries strictly filter by `WHERE owner_uid = $1`. An actual user with their genuine Firebase UID can never query or view records belonging to `staging_test_tiktok_<RUN_ID>`.
- **Potential Risk:** If staging environment uses the production Firebase project or shares the database with human QA testers, uncleaned synthetic rows could accumulate in database dumps or reporting queries.

### 1.6 Safer Alternative for `RUN_ID` Isolation Without Hijacking `owner_uid`
If `owner_uid` must represent a valid, authenticated user (such as a designated staging test user with an authorized Firebase UID `staging-qa-runner-uid`), `RUN_ID` should instead be encapsulated exclusively within:
1. **`idempotency_key`:**
   - Constraint in `V000008`: `CONSTRAINT ck_asset_import_key CHECK (idempotency_key ~ '^[A-Za-z0-9._~-]{1,128}$')`
   - Format: `test_<RUN_ID>_<SEQ>` (e.g. `test_20261108T180000Z9b7e_001`). This complies with `^[A-Za-z0-9._~-]{1,128}$` and does not mutate or pollute `owner_uid`.
2. **`canonical_source_id`:**
   - Format: `synthetic_<RUN_ID>_<VIDEO_ID>`
3. **`normalized_url`:**
   - Format: `https://www.tiktok.com/@staging_test/video/<RUN_ID>_<VIDEO_ID>`

## 2. RUN_ID Isolation Design & Schema Constraints

### 2.1 Schema Length and Format Constraints
| Column | Type | CHECK Constraint / Rule | Max Permitted Length |
| :--- | :--- | :--- | :--- |
| `owner_uid` | `text NOT NULL` | `length(owner_uid) > 0` | Unlimited text (Postgres ~1GB) |
| `idempotency_key` | `text NOT NULL` | `idempotency_key ~ '^[A-Za-z0-9._~-]{1,128}$'` | Maximum 128 characters |
| `command_version`| `text NOT NULL` | Handled by `ck_asset_import_authority` (`= '1.0'`) | Fixed string `'1.0'` |
| `platform` | `text NOT NULL` | Handled by `ck_asset_import_authority` (`IN ('youtube', 'tiktok')`) | Fixed string `'tiktok'` |
| `canonical_source_id` | `text NOT NULL` | No check constraint in V000008 | Unlimited text |
| `normalized_url` | `text NOT NULL` | No check constraint in V000008 | Unlimited text |
| `request_fingerprint` | `bytea NOT NULL` | `octet_length(request_fingerprint) = 32` | Exactly 32 bytes (SHA-256) |

### 2.2 RUN_ID Specification
- **Format:** `RUN_ID = YYYYMMDDTHHMMSSZ_<HEX8>` (e.g., `20261108T180000Z_a1b2c3d4` = 24 chars).
- **Embedded in `idempotency_key`:**
  `test_run_<RUN_ID>_<SEQ>` -> `test_run_20261108T180000Z_a1b2c3d4_0001` (37 characters).
  - Fits easily inside the 128-character limit.
  - Fully satisfies regex `^[A-Za-z0-9._~-]{1,128}$`.
- **Uniqueness & Non-Collision:**
  Combination of UTC microsecond timestamp + 8-hex-digit crypto random guarantee global uniqueness across all execution environments. Sequence IDs within a run (`0001`, `0002`) guarantee distinct primary keys `(owner_uid, idempotency_key)`.

### 2.3 Fail-Closed Handling on Missing, Malformed, or NULL Test IDs
- If `TARGET_RUN_ID` is `NULL`, empty, or does not match regex `^[0-9]{8}T[0-9]{6}Z_[a-f0-9]{8}$`:
  The rollback procedure **aborts immediately** with an explicit error before any query is dispatched.
- Rollback predicate requires exact match:
  `idempotency_key LIKE ('test_run_' || :TARGET_RUN_ID || '_%')`

## 4. Rollback SQL Design Review

### 4.1 Safe Rollback Architecture (Zero Implementation, Pure Design)
When rolling back `V000009` (reverting `ck_asset_import_authority` from `IN ('youtube', 'tiktok')` back to `= 'youtube'`), any row with `platform = 'tiktok'` must be eliminated or the DDL `ALTER TABLE ... ADD CONSTRAINT` will fail with code `23514` (`check_violation`).

To ensure that real or other test runs are NEVER deleted:
1. **Pre-Rollback Audit Query (Fail-Closed Check):**
   ```sql
   DO $$
   DECLARE
     v_non_test_tiktok_count integer;
     v_other_run_tiktok_count integer;
     v_target_run_count integer;
     v_active_jobs_count integer;
   BEGIN
     -- Check 1: Ensure no real non-test TikTok records exist
     SELECT count(*) INTO v_non_test_tiktok_count
     FROM workflow.asset_import_requests
     WHERE platform = 'tiktok'
       AND idempotency_key NOT LIKE 'test_run_%';

     IF v_non_test_tiktok_count > 0 THEN
       RAISE EXCEPTION 'Rollback aborted: Found % non-test TikTok records in workflow.asset_import_requests', v_non_test_tiktok_count;
     END IF;

     -- Check 2: Ensure no other test runs are in an incomplete state
     SELECT count(*) INTO v_other_run_tiktok_count
     FROM workflow.asset_import_requests
     WHERE platform = 'tiktok'
       AND idempotency_key NOT LIKE ('test_run_' || :TARGET_RUN_ID || '_%');

     IF v_other_run_tiktok_count > 0 THEN
       RAISE EXCEPTION 'Rollback aborted: Found % records belonging to other test runs', v_other_run_tiktok_count;
     END IF;

     -- Check 3: Ensure target run records do not have dependent media jobs
     SELECT count(*) INTO v_active_jobs_count
     FROM workflow.asset_import_requests
     WHERE platform = 'tiktok'
       AND idempotency_key LIKE ('test_run_' || :TARGET_RUN_ID || '_%')
       AND (job_id IS NOT NULL OR media_id IS NOT NULL);

     IF v_active_jobs_count > 0 THEN
       RAISE EXCEPTION 'Rollback aborted: Target run records have associated job_id or media_id';
     END IF;
   END $$;
   ```

2. **Targeted DELETE Predicate (Identical to Audit Query):**
   ```sql
   DELETE FROM workflow.asset_import_requests
   WHERE platform = 'tiktok'
     AND idempotency_key LIKE ('test_run_' || :TARGET_RUN_ID || '_%')
     AND job_id IS NULL
     AND media_id IS NULL;
   ```

3. **Post-Deletion Verification:**
   ```sql
   DO $$
   DECLARE
     v_remaining_tiktok_count integer;
   BEGIN
     SELECT count(*) INTO v_remaining_tiktok_count
     FROM workflow.asset_import_requests
     WHERE platform = 'tiktok';

     IF v_remaining_tiktok_count > 0 THEN
       RAISE EXCEPTION 'Rollback aborted: % TikTok records still remain after targeted deletion', v_remaining_tiktok_count;
     END IF;
   END $$;
   ```

4. **Atomic DDL Reversion:**
   ```sql
   ALTER TABLE workflow.asset_import_requests
     DROP CONSTRAINT ck_asset_import_authority;

   ALTER TABLE workflow.asset_import_requests
     ADD CONSTRAINT ck_asset_import_authority
     CHECK (command_version = '1.0' AND platform = 'youtube');
   ```
